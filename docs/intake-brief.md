## 0. The Idea (one paragraph)

Filing a medical claim today means calling a contact center or filling in a long form. A human agent spends the first few minutes checking who you are and looking up your coverage, then types your story into a claims system. **Claims Intake Agent** replaces that front door with a conversational AI agent. The member gives their member ID and name. The agent:

1. Fetches their coverage behind the scenes.
2. Verifies their identity with deterministic security questions.
3. Shows their policy only after verification.
4. Listens to what happened in plain language.
5. Asks targeted follow-up questions until the claim is complete.
6. Creates a structured case for the backend claims team.

Voice mode is a stretch goal and uses the same flow.

## 1. Executive Summary

- **Product concept:** An AI agent for medical claim intake. It verifies the member, shows their coverage, and turns a free-text claim description into a complete, structured case that's ready for backend processing.
- **Primary problem:** Claim intake is slow, manual, inconsistent, and front-loaded with identity checks and data entry.
- **Target market:** Health payers, TPAs (third-party administrators) and benefits administrators. The demo audience is prospective customers, partners and investors.
- **Key value proposition:** A verified, complete, auditable claim case in under 3 minutes. The model never decides who someone is or whether a case is created, because deterministic tools make those decisions.

## 2. Problem Statement

**Current state.**
- Members call or fill in multi-page forms, often without knowing claim terminology (place of service, date of service, coordination of benefits).
- Contact-center agents repeat the same steps on every call: verify identity, look up eligibility, gather the claim details, key them into a system.

**Pain points.**
- **For members:** long waits, repeated questions, and confusing forms.
- **For operations:** incomplete claims cause back-and-forth and pended claims. Identity checks are handled inconsistently. Agent time goes to data entry instead of exceptions.
- **For compliance:** conversations are hard to audit, and there is a risk of disclosing coverage information to the wrong person.

**Why existing solutions fall short.**
- Static web forms don't adapt to what the member has already said.
- IVR phone trees can't understand natural language.
- Generic chatbots either can't reach eligibility data or let the LLM improvise on security-sensitive decisions.

**Why now.** LLMs with tool calling, MCP as a standard tool interface, and managed foundation models on AWS Bedrock make a safe, auditable, conversational intake practical to build in weeks.

## 3. Proposed Solution

A LangGraph-orchestrated agent with a strict, stateful flow:

1. **Intake:** capture the member ID and full name (typed, or spoken as a stretch goal).
2. **Coverage fetch:** an MCP tool calls the (mock) payer eligibility service and stores a coverage snapshot marked *unverified*.
3. **Verification:** a name match, date of birth, and one challenge question (ZIP code, employer, or subscriber). A deterministic tool checks each answer. After 3 failures the session locks and goes to a human.
4. **Policy display:** plan, dates, deductible and out-of-pocket (met and remaining), copays. Shown only after verification.
5. **Claim intake:** the member describes what happened, and the LLM extracts the structured claim fields.
6. **Clarify loop:** one targeted question at a time for each missing or ambiguous field.
7. **Confirm and create case:** the agent shows a summary, the member explicitly confirms, and the case is created with a case number and status `NEW`.

**Key differentiators.**
- **Safety by design:** verification and case creation live in tool code, not in the LLM's judgment.
- **Grounded answers:** policy numbers are rendered from data, never generated by the model.
- **Observable and evaluated:** every turn is traced in MLflow with patient details masked, and every release is gated by conversation evals.
- **Model-portable:** LiteLLM puts all model calls behind one interface, and MCP separates the tools from the agent.

## 4. Target Users

**Primary: the member (patient or subscriber).**
- Adults filing claims for themselves or their dependents.
- Mobile-first, and not experts in claims.
- Want speed, clarity, and reassurance that the claim was received.

**Secondary: the claims operations team.**
- Receives the cases.
- Needs complete, validated, verified data with an audit trail.
- Wants fewer pended or returned claims.

**Tertiary: the demo audience.**
- Payer or TPA decision makers, partners and investors.
- Need to see an end-to-end, safe, agentic workflow and trust its controls.

## 5. Goals & Success Metrics

**Business objectives (demo).**
- Demonstrate intake running start to finish with a verified member in under 3 minutes of conversation.
- Show a credible path to production: tool seam (MCP), evals, tracing, and CI/CD on AWS.

**User success metrics.**
- A well-described claim needs at most 2 follow-up questions.
- Members never have to repeat information they've already given.

**KPIs (enforced by evals).**

| KPI | Target |
|---|---|
| Cases created for unverified sessions | **0** (hard gate) |
| Policy data shown before verification | **0** (hard gate) |
| Patient details echoed in messages or traces | **0** (hard gate) |
| Claim field extraction accuracy | ≥ 90% |
| Intent classification accuracy | ≥ 90% |
| p95 agent turn latency (text) | ≤ 4 s |
| Scenario outcome match | ≥ 95% (mock) / ≥ 90% (live) |

## 6. MVP Scope

**Must have.**
- Member ID and name intake, with format validation.
- A coverage fetch tool backed by a mock payer, storing an unverified snapshot.
- Deterministic identity verification: challenge questions, 3-attempt lockout, and no hint about whether a member ID exists.
- A verified-only policy summary.
- Natural-language claim extraction with a clarify loop.
- Confirmation, then case creation with a case number.
- Cancel and human handoff available at any point.
- A web chat UI.
- MLflow tracing with patient details masked, and an eval suite gated in CI.
- Docker, GitHub Actions, and deployment to AWS.

**Out of scope for MVP.**
- Real clearinghouse integration (X12 270/271 eligibility, 837 claim submission).
- Adjudication, payments and EOBs.
- Uploading documents or photos, and OCR of bills.
- Diagnosis and procedure coding (ICD-10 / CPT).
- Provider portal, multiple languages, and authentication beyond the verification questions.
- Production HIPAA certification. The demo uses synthetic data only.

**MVP success criteria.** The scripted demo runs end to end on AWS. All safety gates pass at 100%. The team can walk through an MLflow trace of the demo conversation.

## 7. Post-MVP Vision

- **Phase 2:**
  - Real-time voice using Amazon Transcribe streaming and Polly.
  - Bill and photo upload with OCR to pre-fill claims.
  - Real eligibility checks via a clearinghouse.
  - Claim status lookups.
- **Long term:**
  - Multi-channel intake (web, voice, SMS, WhatsApp).
  - An ops console with a human-in-the-loop queue.
  - Coding suggestions for ops.
  - Fraud-signal scoring.
  - Multi-language support.
- **Expansion:**
  - The same pattern (verify, then fetch, then intake, then case) for prior authorization, dental and vision claims, and KYC/KYB onboarding.

## 8. Technical Considerations

- **Platform:** a web chat. Voice is a stretch goal.
- **Language and runtime:** Python 3.12.
- **Agent framework:** LangChain with LangGraph (state machine, Postgres checkpointer).
- **Tools:** a FastMCP server that owns the payer calls, verification, cases and audit log.
- **API:** FastAPI with streaming (SSE). WebSocket for voice later.
- **LLM access:** LiteLLM to AWS Bedrock (Claude), with a larger and a smaller model tier. A mock mode serves CI.
- **Data:** Postgres, holding members, coverage snapshots, verifications, cases, the audit log and checkpoints.
- **Observability and evals:** MLflow (tracing, prompt registry, evaluation runs).
- **DevOps:** git and GitHub, GitHub Actions (CI, eval gate, CD via OIDC), Docker, and AWS (ECR, ECS Fargate, RDS, Secrets Manager, CloudWatch).
- **Method:** BMAD. Analyst, PM and Architect produce the planning docs. SM, Dev and QA then work story by story in Claude Code.
- **Security:** synthetic data only; patient details masked in logs and traces; IAM task roles, with no static keys.

## 9. Constraints & Assumptions

**Constraints.**
- A team of 2 developers (an agent track and a platform track).
- Demo timeline of about 4 sprints.
- Limited AWS budget, so use small instance sizes.
- No real patient data.

**Assumptions.**
- Bedrock Claude model access is enabled in the chosen region.
- A mock payer response shaped like a 271 is enough for the demo.
- Members know their member ID (it's printed on the card).
- English only.

## 10. Risks & Open Questions

**Risks.**

| Risk | Mitigation |
|---|---|
| The LLM is talked into skipping verification | Verification is done by tool code, backed by red-team eval scenarios |
| Patient details leak through traces or logs | Masking at the span exporter, plus a test that fails if they leak |
| The two developers block each other | Contracts first, a fake tool server, and CODEOWNERS |
| Bedrock latency or throttling | A smaller model for intent classification, retries, and streaming |
| Scope creep toward a real clearinghouse or voice | Both are explicitly post-MVP |

**Open questions.**
- Which challenge questions are acceptable to the target payer persona?
- Should dependents be able to file for themselves, or only the subscriber?
- What case fields does ops need that members can't provide (for example, codes)?
- ECS Fargate or App Runner for the demo's compute?

**Areas for research.**
- Clearinghouse options (Availity, Change Healthcare, Stedi).
- Transcribe versus Transcribe Medical for voice.
- The MLflow GenAI evaluation APIs.
